# Подготовка и проверка рабочего проекта

## Цель

Подготовить структуру из `Codex.md`: инструкции в `directives/`, Python-скрипты в `execution/`, воспроизводимые промежуточные данные в `.tmp/`.

## Входные данные

Корень проекта определяется по расположению скрипта. Ключи API и доступ к облачным сервисам для этой операции не нужны.

## Инструмент и порядок действий

1. Используй существующий `execution/setup_project.py`.
2. Запусти его из корня проекта: `python execution/setup_project.py`.
3. Проверь сообщения `OK` для трёх папок, `.env` и `.gitignore`.
4. Повторный запуск не должен изменять существующие настройки или дублировать строки исключений.

## Результат

Созданы рабочие папки, заготовка `.env` без секретов и правила `.gitignore` для временных данных, учётных данных и кеша Python. Это инфраструктура проекта; пользовательские результаты рабочих задач размещаются в облачных сервисах согласно `Codex.md`.

## Ограничения и особые случаи

- Скрипт не устанавливает зависимости, не выполняет сетевые запросы и не расходует платные ресурсы.
- Существующий `.env` сохраняется. Существующий `.gitignore` дополняется недостающими правилами.
- `.gitignore` предотвращает добавление новых файлов, но не снимает с отслеживания уже закоммиченные файлы.
- Не создавай фиктивные `credentials.json` и `token.json`. Для задач с Google API нужны реальные OAuth-данные и авторизация пользователя. Наличие файлов само по себе не подтверждает работоспособность доступа.
- В прежнем Windows-окружении команда `python` указывала на неработающий псевдоним WindowsApps; там использовался `C:/Users/InfDesign/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe`. На текущем Mac проверена команда `python3`. После очередного переноса снова проверь путь к интерпретатору.
- Для каждой конкретной рабочей задачи сначала прочитай соответствующую инструкцию и проверь существующие скрипты. При ошибке исправь инструмент, проверь его и дополни инструкцию подтверждёнными сведениями.
- После переноса папки с Windows на macOS не используй скопированный `node_modules`: в нём нет нативного `@rolldown/binding-darwin-arm64`, и Vite не запускается. Выполни `npm ci --include=optional` в корне, `vercel-app/`, `vercel-app/participant/` и `integrations/Leed-generation/` по мере работы с этими приложениями. Lock-файлы сохраняются; после установки проверь запуск Vite. В двух дашбордах доступен `npm run check`; в двух приложениях участника такой команды нет, используй `npm run build`.
- При сборке `vercel-app/` команда `npm run build` собирает и вложенный `participant/`. Если TypeScript сообщает об отсутствующем `react-router-dom` во вложенном приложении, сначала выполни `npm ci --include=optional` в `vercel-app/participant/`, затем повтори сборку из `vercel-app/`.
- Мобильный проект `pavlovdgn-rgb/biletberu-mobile` живёт в отдельном GitHub-репозитории. Для проверки его подключённого сборщика ставь зависимости и запускай `npm run build` внутри этого репозитория. На 9 октября 2026 публичный Production-домен дашборда — `dashboard-woad-one-64.vercel.app`: `/api/health` отвечает 200 без входа в Vercel, `/api/auth` — 401. Служебный `dashboard-alex-p2.vercel.app` перенаправляет гостя на вход из-за Standard Protection; не используй его для ссылок участникам и не отключай защиту, когда доступен Production-домен.
- При изменении экранов Билет Беру сверяй `biletberu-mobile/src/screens/registry.ts` с `vercel-app/execution/mobile_pages.py`: каталог автоматической проверки показывает эти маршруты до первого события. Нажатия и пользовательские события поступают через `task-events` при включённом сборе даже в режиме свободного изучения. Проверь выбор экрана в пустом исследовании тестом `vercel-app/tests/test_cloud_api.py` и собери оба репозитория перед публикацией.
- Для выбора «Нажатие элемента» каталог берёт сохранённые сигналы и клики из всех раундов мобильного проекта (`clicks` + `live_studies`); это нужно для раундов, созданных до появления сигналов условий успеха. Если список пуст, проверь, включён ли сбор кликов и есть ли клики по ссылке участника. Проверка по элементу использует пару `page,target`; короткий идентификатор в интерфейсе помогает различать одинаковые подписи «Кнопка».
- Мобильная тепловая карта сохраняет при каждом нажатии очищенный HTML-снимок состояния страницы и позиции внутренних прокруток. Снимок отправляется отдельным подписанным запросом на `/api/heatmap/snapshots?study=…`; дашборд показывает его без прокрутки и группирует клики по снимкам. Введённые значения полей удаляются. Старые клики без снимка нельзя точно привязать к прежней прокрутке. При проверке после изменений открой ссылку участника, прокрути внутренний список, нажми элемент, затем проверь `context.snapshot`, `data-ux-scroll` в снимке и появление отдельного состояния карты.
- Строка задания в мобильном приложении стоит перед `#root` и занимает 40 px в потоке страницы; высота приложения уменьшается через `--app-height`. При снятии HTML-снимка замени строку пустым блоком той же высоты, иначе координаты кликов на тепловой карте сдвинутся. После изменения проверь на узком экране доступность верхних действий, кнопки покупки и нижней навигации, повторное открытие задания, исчезновение строки после завершения и совпадение снимка с координатами клика.
- В карте Билет Беру нельзя показывать старый клик без снимка поверх живого iframe приложения: пользователь может прокрутить этот фон, а координата останется на месте. Для таких кликов показывай сообщение об отсутствии сохранённого состояния без изображения и тепловой точки. При наличии снимка восстанови его `data-ux-scroll`, заблокируй прокрутку вложенных областей и рисуй слой кликов только после загрузки снимка; эффект рисования должен зависеть от его появления. Проверка в браузере: у старого клика нет iframe/canvas, у нового исходная прокрутка сохраняется после wheel, а пиксель canvas в точке клика непрозрачен.
- Если `/api/heatmap` временно не отвечает после смены экрана или режима, не показывай «0 кликов» на фоне данных другого состояния: сверь `responseKey` с текущими `study/session/group/mode` и дождись ответа для выбранной карты. Ответ `Load failed` в браузере означает сбой загрузки запроса, а не удаление статистики; опрос повторяется автоматически.
- Изображения мобильного приложения бывают не только в `<img>`, но и в inline CSS `background: url("/assets/...")`. В `srcDoc` снимка такой путь разрешается относительно домена дашборда и даёт 404, хотя `<img>` работает. Сборщик должен сохранять абсолютные адреса inline CSS; дашборд должен исправлять относительные `/assets/` при воспроизведении старых снимков. Проверяй это на экране события с фотографиями отзывов: запросов `/assets/` к домену дашборда быть не должно.
- Для передачи сессии из Telegram во внешний браузер мобильный сборщик сохраняет подписанные `ux_study`, `ux_token`, `ux_api`, `ux_session` и `ux_seq` в адресе при переходах по маршрутам приложения. Если встроенный браузер Telegram не передаст полный адрес, участник копирует его кнопкой «Скопировать ссылку» в подсказке. Проверяй этот переход новым браузерным контекстом: должны сохраниться исследование, ключ, сессия и порядковый номер клика. Не выводи реальный ключ участника в журналы и коммиты.
- Удаление исследования подтверждается в модальном окне на странице `Исследования проекта`; сервер удаляет связанные данные в одной транзакции, оставляет снимки, общие с другими исследованиями, и записывает ID в `deleted_studies`, чтобы старые ссылки не возобновили сбор. Схема облака уже была на версии 2, поэтому новая таблица добавляется миграцией версии 3, а не только в `live_project.initialize`. При проверке используй изолированную БД: отмена не меняет данные, удаление выбранного не трогает соседнее исследование, удаление последнего оставляет список и создание работоспособными.
