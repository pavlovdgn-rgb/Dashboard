## Задача
Превратить статичные экраны (из `directive_screens`) в рабочее приложение: подключить навигацию между экранами, слой мок-данных, обработку форм и состояния по действию — включая краевые (edge-cases). Designer задаёт логику (что по какому действию), агент пишет обработчики. На выходе — кликабельный продукт, по которому можно ходить и тестировать.

## Когда применять
- После `directive_screens`: экраны собраны и зарегистрированы в реестре, но статичны (без логики и данных).
- **На любом шаге и многократно:** оживить первый экран, потом другой; добавить новое поведение; позже — анимации. Каждый запуск дополняет. Это не разовый прогон.

## Предусловие
- Собраны статичные экраны и есть реестр/роутер (`src/screens/`), база `src/components/`, токены `src/tokens/`.
- Прочитать `ds/CONTRACT.md` (правила, токены состояний) и `ds/components.md` (какие компоненты под состояния — Toast, Badge, пустые состояния и т.д.).

## Ключевой принцип
Статичные экраны становятся живыми за счёт четырёх вещей: **навигация** (переходы между экранами реестра), **данные** (один слой мок-данных, который экраны читают и меняют), **формы** (ввод → действие → результат), **состояния по действию** (загрузка / пусто / ошибка / успех + edge-cases). Логику задаёт пользователь, обработчики пишет агент — в код пользователь не лезет. Данные — **мок**, без настоящего бэкенда. Всё на семантических токенах (`CONTRACT`).

## Фаза 0. Контекст
Посмотри реестр экранов (`src/screens/registry.*`) и сами экраны — что собрано, какой контент сейчас статикой. Прочитай `CONTRACT` и `components.md` (компоненты под состояния). Определи с пользователем, какой экран/сценарий оживляем в этот запуск (всё сразу не обязательно — можно по одному).

## Фаза 1. Навигация
Сделай навигацию рабочей: клики по пунктам меню, кнопкам и ссылкам ведут на нужные экраны реестра; работает переход «назад» и история; активный пункт меню подсвечивается. Экраны уже зарегистрированы — здесь они становятся реально проходимыми как продукт.

## Фаза 2. Слой мок-данных
1. Заведи **один** слой данных (`src/data/`) — мок-данные, которые нужны экранам (например, список серверов, баланс, операции). Реалистичные, но это мок, не бэкенд.
2. Переведи экраны со статичного контента (вшитого в урок сборки) на чтение из этого слоя. Действия смогут его менять (создал сервер → запись добавилась → список обновился). Это и есть превращение «картинки с текстом» в данные.

## Фаза 3. Формы и поведение
1. Оживи формы: поля собираются, на отправку — действие (добавить запись, изменить данные), с результатом на экране.
2. Валидация ввода: обязательные поля, форматы, границы (пустое, слишком длинное, неверная сумма) → состояние ошибки на поле.
3. **Конкретное поведение задаёт пользователь.** Очевидное из экранов агент вешает сам (submit формы, переход по кнопке, создание → список). Для продуктовой логики, которой нет в макете, — спроси пользователя, что по какому действию должно происходить, и реализуй. Логику формулирует он, пишешь ты.

## Фаза 4. Состояния и edge-cases
Состояния по действию — обязательная часть, не только «когда всё хорошо». Заложи стандартный набор и покажи на экранах:
- **загрузка** (действие в процессе), **успех** (подтверждение, Toast), **ошибка** (действие не прошло), **пусто** (список/данные пустые — empty state);
- **edge-cases**: невалидный ввод, граничные значения (ноль, минус, слишком много/длинно), доменные края (нулевой/низкий баланс → баннер + блокировка действия), «ничего не найдено».
Все состояния — из компонентов базы и семантических токенов (Toast, Badge, баннеры, пустые состояния по `components.md`). **По продукту предложи дополнительные edge-cases**, которых нет в макете, — пользователь решает, какие добавить.

## Фаза 5. Анимации и переходы (опционально, итеративно)
По желанию пользователя — оживить движением: плавные переходы между экранами, появление/исчезновение элементов (добавление в список, тосты, модалки), микро-взаимодействия. Базовые, аккуратные (≈150–250ms, ease). Это можно сделать сейчас или отдельным повторным запуском позже — добавляется поверх, не ломая поведение.

## Фаза 6. Прокликать и проверить
1. `npm run dev`, пройди оживлённый сценарий целиком, как пользователь.
2. Ищи дыры: тупик, откуда не вернуться; действие без реакции; состояние, которое не предусмотрено; кривой переход. Нашёл — правишь через агента, не руками.
3. Покажи пользователю, что подключено; расхождения он называет словами.

## Фаза 7. Повторный запуск = наращивание
Стоячий инструмент. При повторном запуске:
- **ещё экран/сценарий** — оживи его по тем же фазам, остальное не трогай;
- **ещё поведение** — добавь конкретную логику по запросу пользователя;
- **анимации** — добавь движение поверх (Фаза 5).
Существующее не ломаем, мок-слой и навигацию переиспользуем, дубликаты не плодим. В финале перечисли, что добавил.

## Грабли (учтено)

- **Turso: параллельное чтение и запись · 5 октября 2026:** не открывать GET и проверку уже созданной схемы через `BEGIN IMMEDIATE`: они занимают единственный writer и конкурируют с загрузками и опросом настроек. GET использует request-local read-only scope и `BEGIN TRANSACTION READONLY` в libSQL; POST сохраняет атомарную write-транзакцию. Проверять чтение сводки/карты при уже занятом writer и сброс режима чтения перед следующим POST.
  Embedded libSQL 0.1.11 принимает синтаксис READONLY, но сам по себе не запрещает INSERT в локальной in-memory базе. Не проверять по этому свойству облачную маршрутизацию: отдельно проверять синтаксис драйвера, изоляцию HTTP GET от writer и запрос к настоящей Turso.

- **Vercel: запросы сбора · 5 октября 2026:** rewrite может сохранять исходный URL и добавлять служебный `__path`. Нормализовать оба вида URL, а POST-маршруты сравнивать по `urlparse(self.path).path`, не по строке вместе с query. Иначе посещения сохраняются, но клики и снимки получают 404. HTTP-тесты и браузерная проверка облачной версии должны включать запросы с параметрами rewrite; локальный запрос без них не проверяет этот случай.

- **Разделённая кнопка скачивания:** основная область «Скачать» сразу выгружает текущий PNG; отдельная стрелка открывает выбор PNG/ZIP. Это две соседние нативные кнопки с общим видом и разделителем. Обе блокируются при экспорте; у стрелки собственное доступное имя «Варианты скачивания». Открытие меню не запускает скачивание.

- **Настройка и запуск — разные экраны:** `StudySetup` содержит интерфейс, сохранение названия и действующие параметры свободного изучения. `StudyLaunch` содержит проверку API, включение/паузу, показатели поступления данных и инструкцию участнику. Проверка API не означает поступление нового события; последнее действие не равно присутствию онлайн. Заголовок и пункт меню — «Проверка и запуск». Эти экраны получают сводку по всем устройствам, независимо от ранее выбранного аналитического фильтра. Проверка — `execution/check_live_project.py` с отдельной БД, без изменения рабочего сбора.

- **Экспорт карты · 28 сентября:** вместо отдельных кнопок используется «Скачать» (иконка загрузки и шеврон), меню ровно из двух действий: «Текущий экран — PNG» и «Все экраны — ZIP». `HeatmapDownload` собран из ProductAction и EuiPopover/ContextMenu, меню соответствует ширине кнопки. Само изображение ничего не скачивает. Ссылка «К обзору результатов» над картой удалена по последнему указанию пользователя.

- **Кликабельные строки:** общий `Table` делегирует клик по свободному месту строки только её явно отмеченному основному действию `data-row-action`. Ссылки, кнопки, поля и меню внутри строки сохраняют собственное поведение; выделение текста и отключённые действия не запускают переход. Для клавиатуры остаётся нативная ссылка/кнопка, семантика таблицы не заменяется ролью button. Hover и focus-within строки — `accent/soft`.
- **Ручное обновление:** результат показывается отдельным EuiToast справа внизу, без сдвига шапки; успех только после ответа всех обновляемых источников (на карте — сводки и карты). Фоновый опрос не создаёт уведомления. Успех закрывается через 5 секунд, ошибка — через 8; доступно ручное закрытие.

- **Фильтр сессии тепловой карты:** использовать отдельный параметр `session` в маршруте, API и экспорте; `participant` остаётся параметром истории. Фильтровать события до агрегации, включая одинаковые layout у разных сессий, и выбирать фон из той же выборки. При смене сессии не показывать старые точки. Посещение без кликов должно сохранять доступ к выбору всех сессий. Проверка: `execution/check_heatmap_sessions.py` на временной БД. По уточнению пользователя скачивание карты разрешено только кнопками «Сохранить PNG» / «Сохранить все», без обработчика на изображении.

- **Реальное видео по прямому запросу пользователя:** `RecordingControls` запускает getDisplayMedia только по нажатию участника, без микрофона; MediaRecorder пишет WebM в IndexedDB и `/api/recordings`. `SessionVideo` — основной плеер истории, старые снимки свёрнуты и не выдаются за видео. Видимые значения полей в видео не маскируются, предупреждение показано до запуска. Согласие браузера нельзя сохранять или обходить. SPA-переходы сохраняют поток; reload прекращает захват, накопленная часть восстанавливается с отметкой прерывания. После Python-правок перезапускать API. Проверка `execution/check_session_video.py` использует отдельную БД и синтетический источник кадров, не экран пользователя. Для перемотки нужны конечный WebM Duration и HTTP Range; повторная отправка кусочков не должна удваивать запись.

- **Длинный выпадающий список уезжает за экран:** EuiPopover не помещает меню из 24 экранов без ограничения высоты. Ограничивать именно EuiContextMenuPanel (до 20 базовых размеров и 40dvh), включать внутреннюю прокрутку, сохранять ширину поля и клавиатурную навигацию. Проверка: `node execution/check_dropdown_menu.mjs` на широком, низком и мобильном окне; пункты должны оставаться в viewport, включая последний при навигации стрелками.

- **Переход на реальные данные Lead Generation (по прямому запросу пользователя):** основное приложение открывает `LiveWorkspace`, один проект `leed-generation`, исследование `leed-local`. Все аналитические разделы используют SQLite API `/api/project`; компонентные примеры остаются в Storybook. Старый localStorage рабочего пространства архивируется, реальные клики не удаляются. Не смешивать `leed-verify-*` с рабочими данными. Проверка `execution/check_live_project.py` использует временную БД и перенаправляет браузерные запросы к ней. История событий не называется видеозаписью; посещения до миграции и результаты задач не выдумываются. При отключённом API показывать ошибку с последними данными, не переключаться на моки. Для удалённых участников необходим отдельный HTTPS-сборщик; текущие сервисы доступны локально.

- **Одна карта на экран, а не на событие:** DOM-хеш и ID фона хранить для диагностики, но не использовать как основной пользовательский список. Общую плотность суммировать по странице и размеру окна; в интерфейсе один пункт на страницу, размер — отдельный фильтр при необходимости. Фон выбирать из полученных снимков основного экрана; если снимка нет, показывать исходный интерфейс с отключённым сбором. Явно указывать, что это плотность по координатам окна, включая панели. ID фона должен включать viewport: одинаковый HTML адаптивного экрана может иметь разные размеры. Ошибка одного снимка не должна блокировать очередь остальных.

- **Тепловая карта постоянно скрывается из-за хеша состояния:** повторный рендер стартовой страницы не заменяет фон состояния участника. В Lead Generation v2 фон DOM/CSS фиксируется синхронно до React-обработчика; поля очищаются, пользовательский ввод маскируется, скрипты исключаются. Отображать фон в iframe без scripts и с CSP; слой координат отдельно. Исторические события без фона показывать на явно подписанной сетке, а не прятать и не накладывать на выдуманное состояние. Проверять модалку, фильтрацию, вложенный скролл и размеры элементов, а не только клики по пустому месту.

- **Чужой архив с уже подключённой аналитикой:** перед запуском проверить index.html и трекеры. В локальной копии Lead Generation отключён прежний внешний endpoint. Для вложенного скролла сохранять положения контейнеров, восстанавливать их в окне исходного размера и проверять хеш состояния. Одинакового размера экрана недостаточно: фильтры/модалки меняют фон, поэтому несовпадающие состояния не накладываются.

- **Локальный сбор кликов:** измерять clientX/clientY относительно getBoundingClientRect в capture-фазе до перехода страницы; разделять версию, страницу и геометрию. Первый клик выбирать по порядку в сессии до фильтрации размера окна. Повторная отправка должна быть идемпотентной по ID и номеру события. Не отправлять текст, HTML или значения полей. Фон локальной карты — воспроизведение версии NOVA; несовпадающую геометрию не накладывать. Обоснование координат: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect); завершение отправки: [sendBeacon](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon).
- **SQLite на Windows:** контекст `with connection` завершает транзакцию, но не закрывает соединение. Закрывать его явно в finally, иначе файл остаётся заблокированным и проверка перезапуска/очистки не работает.

- **Вкладка превращается в действие при смене раздела:** общую навигацию соседних разделов рендерить одним компонентом с одинаковыми подписями и порядком. Меняется только выбранная вкладка; создание сущности располагается отдельно. Проверять переход туда/обратно, историю браузера и положение панели на мобильной ширине.

- **Хедер и меню уезжают вместе со страницей:** общая оболочка ограничена высотой 100dvh, строка Grid — minmax(0,1fr), вложенная рабочая область — min-block-size:0. Прокручиваются main и длинный sidebar независимо; на мобильном хедер остаётся вне main. Проверять обе композиции оболочки (обзор и остальные разделы), короткий viewport и отсутствие прокрутки документа.

- **Появление скроллбара меняет ширину контента:** резервировать место через scrollbar-gutter:stable у документа и областей с overflow:auto. Проверять реальный scrollHeight/clientHeight: CSS Grid может растянуть внутреннюю область и передать прокрутку документу. Сравнивать координаты и ширину до/после переполнения в приложении и Storybook на широком и узком экране.

- **Пользователь расширяет объём на весь интерфейс:** прежняя граница готовых React-композиций не отменяет новое поручение. Достроить недостающие разделы из существующей базы по макетам и подключить их к общему слою. Не оставлять переходы в сообщение «только в макете».
- **Контекст формы меняется при переходе между исследованиями:** монтировать редактор с ключом ID исследования, чтобы локальный черновик предыдущего исследования не оказался в новом. Проверять цепочку создания, а не только прямое открытие страницы.
- **Высота поиска отличается от кнопок:** одного min-height недостаточно — текст, padding и рамка увеличивают поле. Для компактной панели задавать block-size, box-sizing:border-box и padding-block; проверять фактические границы в браузере.
- **Подсказка ошибки меняет имя поля:** связывать помощь через aria-describedby и сохранять стабильное доступное имя. Проверять не только показ ошибки, но и aria-invalid после отправки.

- **Реестр ещё не существует:** сначала инвентаризировать именно готовые React-композиции. Допустимо зарегистрировать их и оживить этот объём; наличие остальных экранов только в Figma не означает, что они уже реализованы. Явно фиксировать границу запуска в отчёте.
- **Печать из диалога обрезает таблицу:** ограничения высоты и overflow модалки могут оставить в PDF только видимые строки. Выводить тот же снимок данных в отдельную печатную поверхность и проверять последнюю строку и последний столбец экспортированного PDF.
- **Агент тянет настоящий бэкенд/API** — на этом шаге только мок-слой; реальные данные отдельно. Иначе разрастётся не туда.
- **Контент остаётся статикой** — если экраны не перевели на слой данных, действия ничего не меняют. Перевод статики → данные обязателен (Фаза 2).
- **Happy-path-only** — частая недоработка: оживили «когда всё хорошо», забыли пусто/ошибку/границы. Edge-cases — обязательная часть (Фаза 4), не опция.
- **Прибитые значения в новых состояниях** — состояния тоже на семантических токенах и компонентах базы.
- **Повторный запуск ломает сделанное** — наращиваем, переиспользуем мок-слой/навигацию, существующее не переписываем (Фаза 7).
- **Заехали в деплой/метрики** — это следующие уроки; здесь только поведение на моке.

## Дополнение по локальной тепловой карте · 25 сентября 2026

По прямому поручению пользователя добавлены локальный экспорт PNG/ZIP и подписи элементов. При сохранении использовать тот же read-only фон и рендер плотности, что на экране. Ожидать ресурсы статического sandbox iframe снаружи: его собственные таймеры/rAF не исполняются. Старые события не переименовывать по текущему DOM; новые подписи брать только из проверенных статических названий без значений полей и данных клиентов.

Для продуктовых кнопок hover вторичных действий — `accent/soft` с переходом `motion/feedback`. EUI рисует дополнительный `::before` hover-слой, который необходимо отключать в продуктовой обёртке: одного изменения `background-color` недостаточно. Проверять видимость псевдоэлемента, а не только конечный вычисленный цвет. Disabled — светлая нейтральная подложка и приглушённый серый текст, без hover-эффекта.

Составная кнопка «Скачать» использует Secondary: основная область скачивает текущий PNG, стрелка открывает меню PNG/ZIP. Hover и pressed общие для обеих областей, разделитель приглушённый; фокус клавиатуры сохраняется для каждого действия.

Параметры локального исследования `collectVisits`, `collectClicks`, `allowVideo` сохраняются через `/api/project/config`. Для существующих исследований по умолчанию включены все три. Сборщик ждёт первую конфигурацию, затем опрашивает её раз в секунду; до первого успешного ответа сбор выключен. Отключение конкретного вида данных останавливает новые события на клиенте, не удаляя историю и очередь ранее собранных данных. Отключение видео завершает активную запись и сохраняет её. Проверять на изолированной базе через `check_live_project.py` и `check_session_video.py`; рабочую SQLite тестами не изменять. Режимы и проверка целей добавлены 28 сентября 2026; актуальное поведение описано ниже.

Формат записи `recordingMode`: `video` (совместимое значение по умолчанию) или `screenshots`. Второй формат сохраняет последовательность статичных DOM-снимков приложения в `replay_frames`, независимо от аналитических переключателей кликов и посещений; общий `enabled` приостанавливает всё. Кадр клика снимается до обработчика приложения, с нормализованной областью нажатия; после изменения DOM добавляется кадр результата, а после перехода — новый экран. Серия имеет монотонный номер в сессии и очередь IndexedDB для повторной отправки. Одинаковый HTML хранится по хешу один раз. Это не захват рабочего стола и не видео; значения полей маскируются общим snapshot-сериализатором. Плеер показывает только сохранённый снимок, без подмены текущим интерфейсом при ошибке загрузки, и обводку на кадре клика. Сохранённые форматы остаются доступны после переключения. Проверка: `execution/check_session_snapshots.py` (временная SQLite, раскрытый фильтр, выделение элемента, скрытие значений, переходы, очередь/перезагрузка, пауза, отсутствие вызова getDisplayMedia). В тесте дождаться кадра с seq после конкретного клика, а не любого change-кадра: начальная загрузка также меняет экран. Для клика по пункту бокового меню Lead Generation сначала раскрыть flyout наведением на «Генератор лидов».

В продуктовом dropdown меню без треугольного указателя, по ширине якоря и без подчёркивания пунктов. Шеврон поля поворачивается вверх при `aria-expanded=true`, вниз после выбора, Escape и клика снаружи. В нативном ProductField/Select используется фактическое состояние `:open`, а не focus, поскольку закрытый select может сохранять фокус. «Выбрать попытку» использует общий ProductDropdown. Таблица элементов реальной карты имеет компактные строки 40 px вместо 80 px; остальные таблицы этим правилом не затрагиваются.

## Несколько исследований и аналитика · 28 сентября 2026

По прямому поручению пользователя локальный проект Lead Generation поддерживает несколько исследований одного прототипа. `live_studies` хранит отдельные название, сценарий для участника, конфигурацию сбора, формат записи и воронку. `/api/project/studies` создаёт исследование с выключенным сбором. В текущей реализации сценарий — текст задания, не автоматическая оценка его выполнения. Не выдавать посещение страницы за успешное выполнение задания.

Параметр `study` в hash-маршруте и запросах API задаёт контекст организатора; `ux_study` в ссылке прототипа — контекст участника. При смене исследования сбрасывать выбор сессии/кадра и локальные черновики; не показывать предыдущую выборку до ответа нового исследования. Все аналитические чтения, настройки, находки, отчёты, списки видео и снимков должны быть ограничены этим ID. Очереди участника сохраняют исходный ID; повторная отправка не перепривязывает старые события. ID кадров монотонен внутри исследования и сессии, старый ключ последовательности `leed-local` совместим.

Миграция переносит прежний `live_settings.project` в `leed-local` через INSERT OR IGNORE; существующие находки и отчёты получают тот же ID. Историю кликов, посещений, снимков и видео не переписывать. Перед обновлением рабочей схемы запускать `execution/backup_heatmap.py` (SQLite backup учитывает WAL), затем перезапустить только локальный сборщик. Проверки `check_multi_study.py`, `check_live_project.py`, `check_session_snapshots.py`, `check_session_video.py` пишут в временные базы; рабочие данные не использовать для тестовых исследований.

Очередь видео отправляет задания разных исследований независимо: ошибка одного задания не прерывает остальные, а индикатор ожидания/ошибки относится к текущему исследованию. В browser-тесте проверять готовность реальной кнопки записи: динамический import без Vite HMR query может создать другой экземпляр модуля со своим устаревшим состоянием.

«Открыть Lead Generation» остаётся только в настройке исследования и проверке/запуске, высота 56 px. Включение сбора — EuiSwitch без галочки/крестика, подтверждение состояния после API. На странице исследований главное действие «Создать исследование» (56 px, плюс); на странице отчёта — «Сформировать отчёт» (56 px, документ) вместо обновления. «Сохранить PDF / печать» справа непосредственно над сформированным отчётом. Фильтр размера экрана имеет фиксированную ширину 256 px, чтобы смена подписи не сдвигала статус и не сужала меню.

`MetricRatio` использует EuiProgress: обзор — клики экрана / все клики выборки; сигналы — уникальные сессии с сигналом / сессии на экране; воронка — сессии шага / сессии первого шага. Длина полосы соответствует точной доле, подпись округлена. При нулевой базе показывать «—» и пустую полосу. Это показатели активности/наблюдений, не балл качества интерфейса. Проверки: `execution/check_metric_bars.mjs`.

Вариант B фильтров реализован в приложении, но пользователь запросил новую компоновку: варианты D/E тепловой карты и A/B редактора воронки находятся на прежней странице Figma `382:2` (узлы `402:245`, `402:358`, `402:464`, `402:577`). Это варианты для выбора, не утверждённая замена приложения. При передаче изображения в use_figma учитывать ограничение code 50 000 символов; компактный JPEG фона допустим внутри нативно собранного интерфейса.


### Сценарии, критерии и навигация · 28 сентября 2026

- В настройках общий блок «Режим исследования»: `free` / `scenario`. Использовать оформление `SignalViewSwitch` (мягкий оливковый segmented control без обводки), не исходные синие стили EUI. Сценарий и критерий видны только в режиме сценария; переключение в свободное изучение сохраняет черновик задания, отключая его показ для новых попыток.
- `successCriterion`: `none`, `chat_message_sent`, `lead_created`. Критерий проверяется только по подтверждённому действию модели прототипа, не по координате клика или названию кнопки. Текст сообщения и поля лида в событие не входят. Серверная логика — `execution/study_tasks.py`; таблицы `study_task_runs` и `study_task_events`, ключ попытки `(study, session)`. Повторная отправка идемпотентна.
- При старте попытки фиксируются сценарий и критерий. Изменение настройки не пересчитывает старые результаты. Статусы: succeeded («Выполнено»), failed («Не выполнено» после явного завершения без успеха), pending («Без итогового результата»), unassessed (без проверки). Закрытие вкладки не доказывает провал; окончательный неуспех ставится после «Завершить задание». Исторические сессии без критериев не оценивать задним числом.
- Сценарий автоматически открывается в нативном модальном dialog по центру, с клавиатурным фокусом; после закрытия доступна кнопка «Посмотреть задание». Кнопка и плашка записи находятся в общем контейнере слева внизу: вертикальная компоновка с промежутком 8 px не позволяет им перекрывать друг друга при переносах текста. На узком окне отступ от края 16 px. Служебные элементы исключены из снимков и событий. Плашка записи не перекрывает отправку сообщения в чате справа.
- Обзор больше не показывает долю кликов: только числа и переход к карте. Отдельный блок «Выполнение задания» считает выполненные / все сессии с проверкой; незавершённые и неоценённые показаны отдельно. Результат также есть в списке сессий, деталях и новых PDF-снимках отчёта.
- В NavMenu исследования раскрываются отдельной кнопкой; выбор сохраняет раздел, но сбрасывает конкретную сессию/отчёт. Название раздела сайдбара «РАЗДЕЛЫ ИССЛЕДОВАНИЯ» фиксировано по высоте. Выделение следует маршруту сразу, включая hover; заголовок берётся из каталога без ожидания API. При загрузке сохраняется высота контента, повторный выбор использует кэш только своего исследования/размера окна. Старые данные другого исследования не показывать под новым названием.
- Копирование ссылки подтверждается заметным toast справа сверху на 5 секунд, вне потока документа; ошибка копирования также видна, поле выделяется для Ctrl+C.
- Проверки: `check_study_tasks.py StudyTaskTests.test_outcomes StudyTaskTests.test_browser_tasks` (изолированная SQLite; настоящее сообщение через UI; открытие чата и пробелы не успешны; неуспех/незавершённость/изоляция/отчёты/модальное окно/toast/задержка API при смене исследования). `check_multi_study.py` и `check_live_project.py` — регрессии. Не переопределять `event()` родительского теста: это фабрика кликов; использовать `task_event()`.

## Несколько заданий и выбор исследования · 28 сентября 2026

- Актуальная модель — `tasks` со стабильными ID, названием, инструкцией и критерием. Редактор работает в режиме «По сценарию»; перестановка и удаление представлены иконками с подсказками. Примечание под сохранением — небольшой вторичный текст.
